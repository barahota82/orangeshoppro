No Restore implementation begins until this owner policy is archived and acknowledged.

any Restore design or code work.

================================================================================
1. Restore must NEVER run automatically
================================================================================
- No Scheduled Task.
- No Cron.
- No background worker.
- No unattended restore.

================================================================================
2. Restore must NEVER be exposed through public or automatic triggers
================================================================================
Restore must NEVER be exposed through:
- public endpoint
- webhook
- URL trigger
- command executed automatically
- normal admin permission

================================================================================
3. Restore is restricted to Super Admin + dedicated permission
================================================================================
- Restore operator must be **Super Admin**.
- Introduce a dedicated permission: **backup_restore**
- No other admin role may execute restore.

**تنفيذ:** Permission `backup_restore` and Super Admin gate — **not implemented** (Phase 2+).

================================================================================
4. Restore requires explicit re-authentication
================================================================================
The current logged-in session is **NOT** sufficient.
Before any restore begins, the operator must authenticate again.

**تنفيذ:** Re-auth step before restore — **not implemented** (Phase 2+).

================================================================================
5. Restore requires high-friction confirmation
================================================================================
Example — operator must type exactly:
- RESTORE
- or RESTORE KUWAIT (country-scoped restore)

No one-click restore.

**تنفيذ:** Typed confirmation UI/step — **not implemented** (Phase 2+).

================================================================================
6. Mandatory restore workflow (direct production restore forbidden)
================================================================================
Step 1 — Validate package (DRV / verify CLI).
        ↓
Step 2 — Create a fresh Full Disaster Backup.
        ↓
Step 3 — Restore into **STAGING** (never production first).
        ↓
Step 4 — Run Disaster Recovery Validation on staging result.
        ↓
Step 5 — Owner reviews results.
        ↓
Step 6 — Explicit approval.
        ↓
Step 7 — Production Merge.

**Direct production restore is forbidden.**

**تنفيذ:** Staging restore, production merge, admin workflow — **not implemented** (Phase 2+).
Read-only validation exists: Phase 1C DRV (`validate_backup_recoverability.php`).

================================================================================
7. Country Restore and Full Restore are separate operations
================================================================================
- Separate permissions.
- Separate workflow.
- Separate audit trail.

Country Recovery Package (CRP) restore and Full Disaster restore must not share
a single undifferentiated code path or permission.

**تنفيذ:** Separate Full vs Country restore paths — **not implemented** (Phase 2+).

================================================================================
8. Permanent audit record for every restore operation
================================================================================
Every restore operation must create a **permanent, non-editable** audit record.

Minimum fields:
- operator
- timestamp
- source package
- package checksum
- package version
- schema revision
- country / full (scope)
- staging target
- production merge approval
- duration
- result

Audit entries must never be editable.

**تنفيذ:** Restore audit log storage/UI — **not implemented** (Phase 2+).

================================================================================
9. No silent destructive actions on production
================================================================================
Restore must never delete existing production data silently.
Every destructive action must be explicit and logged.

**تنفيذ:** Explicit destructive-step logging — **not implemented** (Phase 2+).

11. Production Merge Credentials (Permanent owner decision — 2026-07-13)
================================================================================
Production Merge must **never** use the normal application MySQL account (`DB_USER` /
`DB_PASS` from `.env.php` / `config.php`).

Production Merge must always use a **dedicated** server-only account:

  ORANGE_RESTORE_MERGE_DB_USER
  ORANGE_RESTORE_MERGE_DB_PASS

Rules:
- Separate from `DB_USER` / `DB_PASS`
- Separate from `ORANGE_RESTORE_STAGING_DB_USER` / `ORANGE_RESTORE_STAGING_DB_PASS`
- Production database schema only (`DB_NAME`)
- Minimum privileges required for merge (operator grants manually on server)
- Never reused by the web application, storefront, admin, or routine backup jobs
- Documented in `.env.example.php`, `docs/archive/ORANGE_RESTORE_ARCHITECTURE.txt`,
  and `docs/archive/ORANGE_BACKUP_RECOVERY_RUNBOOK.md`

**Fail closed:** If merge credentials are missing, empty, or equal to the application
or staging restore user/password, Production Merge must abort before any production write.

**تنفيذ:** Dedicated merge credentials + fail-closed gate — **architecture approved;
not implemented** (Phase 2D.1).

================================================================================
12. Uploads cutover volume safety (Permanent owner decision — 2026-07-13)
================================================================================
Full Disaster Production Merge uploads cutover strategy (approved):

  uploads_next  →  directory rename swap  →  uploads

Before any production uploads cutover, the system **must** verify that live `uploads/`
and prepared `uploads_next/` are on the **same filesystem / volume** so directory rename
is atomic on the approved path.

If they are **not** on the same volume:
- **Abort the merge fail-closed** before any production uploads modification

**Forbidden** (no silent fallback):
- recursive copy
- merge / partial merge of uploads trees
- move
- copy-then-delete
- any non-atomic alternative

Rationale: directory rename is the only approved production uploads cutover strategy.
If atomic rename cannot be guaranteed, merge must not proceed to uploads cutover.

**تنفيذ:** Same-volume verification gate — **architecture approved; not implemented**
(Phase 2D.1).
