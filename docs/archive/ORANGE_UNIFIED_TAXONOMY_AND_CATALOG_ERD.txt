ORANGE — التصنيف الموحّد (Unified Taxonomy) + مخطط ERD + ترحيل
================================================================
المسار: docs/archive/ORANGE_UNIFIED_TAXONOMY_AND_CATALOG_ERD.txt
تاريخ اعتماد المالك (سياسة نهائية قبل Patch): 2026-04-26
مرحلات التنفيذ المتوقعة: شجرة المنتج + صفات + مقاسات + ألوان + أنماط + واجهة وأدمن (على خطوات، لا كتلة واحدة).


--------------------------------------------------------------------
أولاً — القرار الملزِم للمشروع (ملخص تنفيذي)
--------------------------------------------------------------------

1. **نظام تصنيف واحد فقط (Unified Taxonomy)** يغذّي:
   - التنقل (Navigation / القوائم)
   - الفلترة (Filter system)
   - بنية البيانات (Data structure — مصدر واحد للحقيقة في الكتالوج)

2. **لا Taxonomy موازية**؛ **لا نظام قديم + جديد**؛ لا ربط المنتج بمسارات تصنيف متعددة مستقلة.

3. **عمق الشجرة النهائي (قبل SKU):**
   Department → Section → Category → Subcategory → ProductType

4. **المنتج يربط بالورقة العميقة فقط:**
   **`products.product_type_id`** → `product_types.id`
   لا يعتبر **`department_id` / `category_id` / `subcategory_id`** على المنتج (إن وُجدت أثناء انتقالية) سوى **مشتقّة أو Cache أو قيد ترحيل** حتى تصبح لاغية، وليست مصدر الحقيقة.

5. **الصفات (Attributes)** منفصلة تمامًا عن مستويات الشجرة؛ أمثلة: عدد القطع، طول الكم، طول القصّة، الخامة، الموسم، المناسبة، نوع الإغلاق، الخصر، نوع الكعب، **نوع المقاس (كصفة دلالية)** إلخ. التفاصيل الدقيقة لا تُستبدل بمستوى «Category» ثابت.

6. **`offers` / العروض** ليست عقدًا في الشجرة؛ هي **طبقة عرض / استعلام / ترويج** فقط (`View / Query / Promotion layer`).


--------------------------------------------------------------------
ثانياً — أسماء الجدايل المقترحة (نهائية للتخطيط الأول Patch)
--------------------------------------------------------------------

التسمية مراعية لكون المستودع يحتوي فعلًا على **`categories`** و **`subcategories`** اليوم؛ الهدف بعد الترحيل **عدم احتمال جدولين لنفس المستوى**. الأسماء أدناه هي **أسماء منطقة الكتالوج الموحّد** (مع إمكان تنفيذها بإنشاء جدايل جديدة ثم قطع علاقات القديمة، أو إعادة تسمية مرحلية وفق مخاطر FK).

المستوى | الجدول (نهائي مخطَّط)           | علاقة الأم
--------|----------------------------------|------------------
1       | **`departments`**                | —
2       | **`catalog_sections`**           | `department_id` → `departments.id`
3       | **`catalog_categories`**         | `catalog_section_id` → `catalog_sections.id`
4       | **`catalog_subcategories`**       | `catalog_category_id` → `catalog_categories.id`
5       | **`product_types`**               | `catalog_subcategory_id` → `catalog_subcategories.id`
منتج    | **`products`**                  | **`product_type_id`** → **`product_types.id`** (مصادر الحقيقة للتصنيف)

حقول عامة مشتركة (كل مستوى عقدة ما عدا التعدد في المنتج):

- **`slug`** أو **`catalog_key`** فريد **ضمن الأم** أو **عالمياً حسب قرار واحد ثابت** (يُحدَّد في مرحلة الـ DDL؛ يُفضَّل مفتاح إنجليزي ثابت `women`, `tops` … للاستعلام ولعناوين URL).
- أسماء عرض: **`name_ar`, `name_en`, `name_fil`, `name_hi`** (انسجاماً مع سياسات اللغة في المتجر)، **`sort_order`, `is_active`, `created_at`** حسب النمط الحالي للمشروع.

**جدول المنتج (فئة التصنيف فقط)** — مستقل عن الألوان/المخزون:

- **`products.product_type_id`** (NOT NULL بعد اكتمال الترحيل).
- عمود احتياطي ترحيلي (اختياري عبر مراحل): `legacy_category_id`, `legacy_subcategory_id` **قابل للإسقاط** بعد التحقق.

**ملحق كتالوج قائم اليوم لا يُلغَى منطقيًا:**
- **`size_families` / `size_family_sizes`**، **`color_dictionary` / `pattern_dictionary` (أو ما يكافئهما)**، **`product_colorways`**, **`product_variants`**، **`product_images`**, **`product_channels`** إلخ.
- سياسة الربط: **عائلة المقاس وألوان/أنماط المتغيرات** تظل مع **SKU**؛ ربط **اقتراح/تحقّق نوع مقاس مقبول حسب تصنيف** يتم لاحقاً عبر صفات أو قواعد `product_types` وليس بتكرار مسار SKU داخل الشجرة.


--------------------------------------------------------------------
ثالثاً — طبقة الصفات Attributes (جدوليان على الأقل)
--------------------------------------------------------------------

جدول **التعاريف**:

- **`catalog_attributes`**
  - `id`
  - `attribute_key` (مثلاً `piece_count`, `sleeve_length`, `fabric`, …) فريد
  - حقول عنوان للعرض: `label_ar`, `label_en`, `label_fil`, `label_hi`
  - `input_kind` أو ما يكافئ: `enum_single`, `multi`, `boolean`, `text_short` …
  - `is_filterable`, `sort_order`, `is_active`

جدول **ربط منتج إلى قيم** (التخزين أبسط في المرحلة 1؛ يمكن تطبيع قيم enums لاحقاً):

- **`product_attribute_values`**
  - `id`
  - `product_id` → `products.id` **ON DELETE CASCADE**
  - `catalog_attribute_id` → `catalog_attributes.id`
  - `value_raw` أو `enum_value_key` أو JSON صغير **ضمن سياسة واضحة** (يُثبّت في Patch الأول لقيم الحقول المحدودة)

**اختياري لاحقاً** (توسّع دون كسر النموذج):

- **`catalog_attribute_options`** (قيم جاهزة لكل `attribute_key` + الترجمة).
- **`product_type_attribute_required`** (أي صفة إلزامية لكل ProductType).

رابعاً — مخطط ERD علاقات (نسخة نصية)
--------------------------------------------------------------------

    departments (1)
       │
       └──< catalog_sections (N)  ─ department_id
                 │
                 └──< catalog_categories (N) ─ catalog_section_id
                           │
                           └──< catalog_subcategories (N) ─ catalog_category_id
                                     │
                                     └──< product_types (N) ─ catalog_subcategory_id
                                               │
                                               └──< products (N) ─ product_type_id


    products (1)
       │
       └──< product_attribute_values (N) ─ product_id


    catalogs منفصل عن SKU:
    products (1) ──< product_variants ── مخزون / لون كمرجع / مقاس كنص ومفتاح famille
                          │
                          └── (طبقات colorways موجودة؛ لا تدمج مع عقد taxonomy)


--------------------------------------------------------------------
خامساً — العروض Offers (طبقة خارج الشجرة)
--------------------------------------------------------------------

- لا يوجد `offers` كـ `product_types` إلزامي.
- يُنفَّذ كـ: قواعد عروض قائمة / خصومات / قنوات عرض / استعلامات «جمع منتجات من أقسام أخرى» — كما في مسارات المشروع الحالية (`cart_promotions`، قنوات، إلخ) دون جعل «العروض» فرعاً في شجرة الكتالوج.


--------------------------------------------------------------------
سادساً — الوضع الحالي في الكود ومخطّط الترحيل (بدون تنفيذ هنا)
--------------------------------------------------------------------

واقع المستودع (ملخّص، لمراجعة `includes/catalog_schema.php` وملف الإنشاء الكامل):

- **`departments`**: الأعلى موجود.
- **`categories`**: مربوطة بـ `department_id` (اليوم هذا المستوى يعبِّر عملياً عن «فئة تحت القسم» دون مستوى `Section` المعتمد الآن سياسًيا).
- **`subcategories`**: مربوطة بـ **`categories`**.
- **`products`**: يحوي **`category_id`** و **`subcategory_id`** (لا يوجد عمود `department_id` مباشر على المنتج في القالب المرجعي؛ القسم يُستنتج من الفئة حيث يكون `department_id` على `categories`).

**خطوات ترحيل مقترحة (بالترتيب؛ تُناقش وقت التنفيذ مع نسخة احتياطية):**

**المرحلة A — تهيئة مخطّط الموحّد**
1. إنشاء **`catalog_sections`** وربطها بـ `departments`.
2. إنشاء **`catalog_categories`**؛ إنشاء **`catalog_subcategories`**؛ أو ترحيل بيانات من **`categories`** / **`subcategories`** بحسب قرار واحد (**نسخ أو إعادة تسمية**) مع احترام كل FK موجودة اليوم إلى تلك الجدايل.
3. إنشاء **`product_types`** وتوزيع كل «ورقة تجارية» حقيقية (مثل نوع منتج قبل SKU)؛ يمكن بدء قائمة فارغة وإنشاء ورقة افتراضية «بدون تصنيف دقيق» مؤقتة لتجاوز NOT NULL (**فقط لفترة الاختبار** إن لزم).
4. إضافة **`products.product_type_id`** (NULLABLE ثم تعبئة ثم NOT NULL بعد التحقق الكامل).

**المرحلة B — تعبئة وربط**
5. كل منتج موجود: تصوّر ورقة **`product_types`** واحدة لكل SKU-group الحالي؛ إن لم تكن موجودة ورقة تجارية حقيقية، تُنشأ ورقة اسمها مؤقتة من الاسم العربي أو من `slug` **`legacy-subcategory-topic`** لتفادي خطأ بيانات.
6. تشغيل **سكربت ترحيل** يُملأ **`product_type_id`** من (`category_id`,`subcategory_id`) أو يدويًا عبر لوحة تصحيح.
7. تعطيل اعتماد المسارات القديمة في التطبيق: استعلامات الواجهة والأدمن تُنشأ انطلاقًا من **`product_type_id`** + JOIN واحد أو عرض (**materialized**) للأعلى.

**المرحلة C — صف العمود الآمن قبل الإسقاط**
8. إن وُجدت أعمدة Cache للأعلى (**`computed_department_id`** …)، تُحمَّل بطريقة مهيأة للخروج من المسار الساخن بثقل (انظر `ORANGE_STOREFRONT_PERFORMANCE_ROLLOUT.txt`).
9. بعد التحقق: إسقاط أو إهمال **`products.category_id` / `products.subcategory_id`** وإعادة فهرسة الاستعلامات.

**المرحلة D — Attributes**
10. إدراج تعريفات **`catalog_attributes`** ثم قيم **`product_attribute_values`** على دفعات.

**ملاحظة مخاطر الترحيل:** أي FK من جدايل أخرى تشير إلى `categories`/`subcategories` (مثلاً قنوات، تقارير، إن وُجد) يجب فحصه قبل إسقاط الجدايل القديمة.


--------------------------------------------------------------------
سابعاً — تزامن مع ألوان/أنماط/مقاسات
--------------------------------------------------------------------

- **لا تُستبدل** صفوف **`product_variants`** بعقد taxonomy.
- **`product_types`** يمكن أن يحمِل مستقبلًا حقول دلالية (**`expected_size_scheme_key`** أو ربط بصفة **`نوع المقاس`** في `catalog_attributes`) لاستخدام لوحة تحقق أو اقتراح عائلات مقاس؛ هذا **Patch مستقل** لا يفسد ترحيل التصنيف.

**ملحق «سابعاً ب»: هرَم المقاس الأربعة — نطاق قياسي تجاري (ليس شجرة التنقل الموحّدة)**

⚠️ **تمييز أسماء (إلزامي لفهم الوكلاء):**
- **`product_types` (جدول المتجر الموحَّد)** = ورقة عمق شجرة **التنقل/الكتالوج** قبل SKU (مثل *Pajama Set* وباقي أوراق المتجر الموحَّد).
- الـ «**Product Type**» في هرَم المقاس الذي يصفه المالك أدناه = **المستوى الأول لنطاق المقاس التجاري** (`commercial_kind` في الوثائق هنا)، بمفاتيح مثل: `clothing`, `shoes`, `bags`, `accessories` — **ليست اسم الجدول** `product_types` أعلاه.

**المستويات الأربعة لسياسة المقياس:**

| مستوى | الدور | أمثلة مفاتيح (إنجليزي ثابت) |
|-------|-------|-------------------------------|
| 1 | النوع التجاري لمِدار المقاس | clothing, shoes, bags, accessories |
| 2 | فئة ضمن النوع (تخطيط الفلترة وقواعد العائلات) | ملابس: tops, bottoms, sets, dresses — أحذية: sneakers, sandals, boots — … |
| 3 | عائلة مخطّط مقاس (**Size Family كقالب أو مفتاح مخطّط**) | clothing_alpha, clothing_numeric, shoes_eu, kids_age, baby_months, one_size |
| 4 | مقاس قابل للبيع (صف قيم؛ اليوم **`size_family_sizes`**) | S, M, L — 30, 32 — 40, 41 إلخ |

**سياسة تجنّب الغلطة:** لا تُربَط **`size_family` / `size_family_id`** **بمنتج وحده** بدون اعتبار المنطقي للمستويين **1 و2** (أو بدون آلية مستندة لهما: حقول مشتَّقة، أو قالب، أو جدول وسيط)، حتى لا تتكرر العائلات بلا سبب وتضعُف الفلترة والتوسّع لاحقاً.

**أمثلة حقول منطقية (الي JSON توضيح لسياسة البيانات — ليس إلزام عمود JSON على المنتج):**

- تيشيرت: `commercial_kind`: clothing ، `sizing_category`: tops ، `size_scheme_key`: clothing_alpha ، `sizes`: [S,M,L].
- بنطلون: clothing ، bottoms ، clothing_numeric ، [30,32,34].
- حذاء: shoes ، sneakers ، shoes_eu ، [40,41,42].
- كاب: accessories ، hats (أو ما يُعادله في الجدولة) ، one_size ، وقد لا تُنشأ كل قيم مستوى 4 عند «مقاس موحّد».

**الجدايل/التكامل تقريبًا مع الكود اليوم:**
- مستويات **3 و4**: تتوافقان مع **`size_families`** و **`size_family_sizes`**؛ يُفضّل تعزيز مستوى 3 بعمود مثل **`size_scheme_key`** (أو ما يُسمّى)، واضباط ربط اختياري بالمستوىين 1–2 عبر **جدول وسيط** أو **صفات**.
- مستويان **1–2**: إمّا **جدايل مرجعية** (`commercial_kind_keys`، `sizing_category_keys`)، أو تعبئة عبر **`catalog_attributes`** أو استنتاج تحكم من ورقة **`product_types`** الشجرية الموحَّدة بحيث **لا توجد taxonomy موازية للعرض للعميل** — بل **قواعد قياس تنبثق من نفس المصدر الموحَّد**.
- **`product_sizes`** (إن اُعتمد مستقبلًا): اختيار فرعي لقيم مستوى 4 لمنتج معيّن دون بيع عمود القائمة كاملاً.

**التجسير مع النظام الموحّد (بدون نقض قرار واحد قبل SKU):**
- مصدر حقيقة **ظهور المنتج تحت أي قسم متجر** يبقى **`products.product_type_id`**.
- **هرَم المقاس الأربعة** لا يكون «شجرة واجهة ثانية»؛ يُكمَّل بتعيين **`products.size_family_id`** وفتح **`product_variants`** وفق مخطّط مختار وفق هذه القواعد.

سابعاً-مكرر — كود الصنف الرقمي (item_code) — قرار المالك 2026-06-16
--------------------------------------------------------------------

`products.item_code` صار **كوداً رقمياً بحتاً** يعكس مسار الشجرة الموحّدة (بدل الـ slug اللاتيني السابق):

```
DD SS CC UU TT NNNN   →   مثال: 01 02 03 01 05 0001  =  01020301050001  (14 رقماً)
```

- DD = القسم (Department)، SS = قسم الكتالوج (Section)، CC = الفئة (Category)، UU = تحت‑الفئة (Subcategory)، TT = نوع المنتج (ProductType) — **خانتان لكلٍّ**، والرقم = **ترتيب العقدة داخل أبيها** حسب `(sort_order, id)`.
- NNNN = **تسلسل المنتج داخل نوع المنتج** (4 خانات) حسب `(sort_order, id)`.
- **الترقيم مُشتق تلقائياً** (قرار المالك: auto وليس عمود code مخصّص)؛ لذلك **قد يتغيّر** كود منتج عند إعادة ترتيب/حذف عقدة أسبق ثم إعادة حفظ المنتج. لا يوجد قيد UNIQUE على `item_code` فلا أخطاء تصادم.
- إن تجاوز مستوى **99 ابناً** (أو المنتجات **9999** داخل النوع) يتمدّد عدد الخانات بدل التصادم (الطول يصبح أكبر من 14).
- **التنفيذ:** `includes/catalog_unified_product_helpers.php` — `orange_catalog_generate_product_item_code_from_tree()` + المساعدان `orange_catalog_node_ordinal()` و`orange_catalog_product_ordinal_in_type()`. يُستدعى تلقائياً في `admin/api/products/create.php` و`admin/api/products/update.php` (يُعاد التوليد دائماً عند وجود `product_type_id`).
- **المنتجات القديمة:** تبقى بأكوادها السابقة حتى إعادة حفظها؛ لإعادة ترقيمها دفعة واحدة استخدم `scripts/backfill_numeric_item_codes.php` (CLI، آمن لإعادة التشغيل): `php scripts/backfill_numeric_item_codes.php`.
- الاحتياطي في التقارير عند غياب الكود يبقى `P{id}`.
