0) ملخص قرار المالك (2026-05-20 — نقاش + تأكيد)
================================================================================

ARABIC
- **المشكلة:** فواتير **المشتريات** و**مردود المشتريات** بُنيت كـ **مستند v2** (شاشة واحدة: إنشاء + عرض + تعديل + بحث + تنقل + طباعة + قفل). فواتير **البيع** و**مردودها** (شركة + أونلاين) **لا ترقى** لنفس المستوى — مسار مجزّأ: قائمة بحث منفصلة + شاشة إنشاء بدائية.
- **الهدف:** **شاشة واحدة لكل نوع** = نفس **قالب** `purchases` / `purchase_returns` — **بحث من داخل الفاتورة** (modal + << < > >>) — **لا** شاشات قائمة مستقلة للتصفّح فقط.
- **المرجع البصري/السلوكي:** `admin/pages/purchases.php` + `admin/pages/purchase_returns.php` + APIs المقابلة (`admin/api/purchases/*`, `admin/api/purchase_returns/*`).

ENGLISH
- Unify sales invoice UX with purchase document v2: single screen per doc type, in-document search/nav, edit_lock, print, ancillary lines, product pick — preserve distinct backend policies (INV-C vs INV-O, stock/GL lanes).

1) سياسة العميل — ليس «ضيفاً بلا سجل»
================================================================================

ARABIC (قرار مالك — يكمّل س2 في ORANGE_STOREFRONT_POLICY_REFERENCE)
- على **الواجهة** يُسمح بالشراء **بدون حساب موقع** (ضيف عربة) — اسم + هاتف + منطقة + عنوان.
- في **فاتورة الشركة (الأدمن)** وعند **إتمام/تسليم** الطلب: **كل بيع له هاتف صالح** يُسجَّل/يُحدَّث في **`customers`** ويُربَط بـ **`orders.customer_id`** — **لا** فاتورة «بدون عميل في النظام» بعد الحفظ.
- **التنفيذ الحالي (يُحافظ عليه):** `orange_ensure_customer_with_profile()` في `includes/order_fulfillment.php` (س15) — يُستدعى من `admin/api/orders/create-manual.php` عند الحفظ.
- **الواجهة الجديدة:** اختيار عميل **مثل المورد** — **كود + اسم + نقر مزدوج** + **رصيد ذمم (AR)**؛ عميل جديد من الترويسة (اسم + هاتف + منطقة + عنوان) → يُنشأ في `customers` عند الحفظ.
- **غير مسموح:** حفظ فاتورة شركة **بدون اسم + هاتف** على الأقل.

ENGLISH
- Storefront guest checkout OK; admin company invoice must tie to customers row via phone; UI mirrors supplier picker + AR balance.

2) قناة العملاء — واتساب حتى ينتشر الموقع
================================================================================

ARABIC (سينario تشغيلي — قرار مالك)
- العميل يطلب عبر **واتساب** (أو قناة أخرى)؛ الموظف يُدخل الطلب من **فاتورة الشركة** لراحة العميل.
- **حقل «قناة العملاء» إلزامي** (أو شبه إلزامي) في ترويسة المستند — يُسجَّل البيع **`orders.channel_id`** لتقارير القنوات (`channel_analytics`) حتى يُستخدم الموقع على نطاق أوسع.
- **لا** مخزن منفصل per قناة — مخزن الشركة الموحد (س1 أرشيف الواجهة).
- **التنفيذ الحالي:** `channel_id` في `manual_order.php` + `admin/api/orders/create-manual.php` + `order_source = company`.

ENGLISH
- Company invoice = manual order entry + channel attribution for WhatsApp/TikTok etc.; single warehouse.

3) الفرق المحفوظ — شركة vs أونلاين (لا تُدمَج السياسات الخلفية)
================================================================================

| | فاتورة شركة INV-C | فاتورة أونلاين INV-O |
|---|---------------------|----------------------|
| المصدر | `order_source = company` | طلب `website` → `completed` + INV-O |
| المخزون | خصم **فوري** عند حفظ الشركة | حجز → خصم عند الإكمال (س1) |
| GL | **فوري** عند حفظ INV-C (`create-manual`) | لاحقاً من «إنشاء القيود» + مسارات §13 (س29) |
| **الواجهة المستهدفة** | مستند v2 **كامل** (إنشاء/تعديل/…) | **نفس القالب** — قرار مالك: **تعديل مثل الشركة** (ليس عرض/طباعة فقط) |
| Backend | APIs طلبات + fulfillment | APIs `orders/update.php`, `amend-invoice-items.php`, … — **يُعاد استخدامها/توسيعها** دون كسر س25/س26 |

**ملاحظة للوكيل:** توحيد **UI/UX** ≠ دمج جدول أو مسار GL واحد.

================================================================================
4) ما **لا** يدخل فاتورة الشركة اليدوية
================================================================================

- **عروض العربة** (BOGO، هدية سلة، كومبو، خصم مجموع سلة للمسجّلين) — مسار **`cart.js` / `checkout-preview`** — **لا** تُطبَّق تلقائياً على فاتورة الشركة اليدوية.
- **يُبقى:** نوع البيع (نقدي/آجل/أونلاين)، **مدفوع الآن**، بنود إضافية GL، خصم سطر/فاتورة يدوي من الشاشة.
