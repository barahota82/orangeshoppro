================================================================================
CLI-first architecture (Permanent owner adjustment #2)
================================================================================

All restore **business logic** lives in CLI scripts and `includes/backup/restore/*`.
Future Admin UI is a **thin wrapper only**:

    CLI Engine (scripts/backup/restore_*.php + includes/backup/restore/*)
            ↓
    Admin UI Wrapper (Phase 3 — invokes same CLI/orchestrator)
            ↓
    Operator (Super Admin + permission + re-auth + confirmation)

**Rules:**
- Admin pages/APIs must NOT duplicate restore logic (no SQL import, merge, or
  validation algorithms in admin/api/restore beyond spawning CLI and displaying output).
- Admin UI passes operator credentials into the same gates as CLI (re-auth, permissions,
  typed confirmation, approval token).
- No public endpoint, webhook, scheduled task, or background worker may invoke restore.

================================================================================
Rollback policy (Permanent owner adjustment #3)
================================================================================

**The ONLY production rollback anchor** for a restore job is the **Stage 3 Fresh
Full Disaster Backup created inside that same restore job** (recorded on the job as
`fresh_backup_path` + `fresh_backup_checksum` with `rollback_anchor_job_only=true`).

- Older snapshots (including pre-job manual backups) must **never** automatically
  become rollback anchors.
- If Stage 3 fresh backup fails or is missing, merge must not proceed.
- Post-merge rollback (when implemented) restores production from **that job's**
  Stage 3 backup only — not from arbitrary older packages.

================================================================================
Mandatory restore pipeline (both Full and Country)
================================================================================

1. Package Selection
2. Package Validation (Phase 1C DRV + verify)
3. Fresh Full Disaster Backup (rollback anchor for THIS job)
4. Staging Restore (Phase 2B.1 — full disaster → staging CLI only)
5. Staging Validation (post-restore checks + DRV-style staging report)
6. Owner Review
7. Explicit Approval (typed phrase + approval token)
8. Production Merge (Phase 2D — forbidden direct-to-production)
9. Post Validation
10. Audit finalize

Country Restore and Full Restore use **separate** permissions, CLIs, merge engines,
and audit scope (`full_disaster` vs `country_recovery`).

**Scope (2B.1 only):**
- CLI-only full disaster restore into isolated staging DB + staging uploads under restore work dir
- Pre-check: existing package verify + Phase 1C DRV (abort on failure)
- **Package compatibility gate:** `export_backend=php_pdo` only; mysqldump/PowerShell/DELIMITER dumps rejected **before** staging mutation
- Stage 3 fresh full disaster backup → rollback anchor on job (**mandatory — no bypass flag**)
- Dedicated staging MySQL credentials (`ORANGE_RESTORE_STAGING_DB_USER` / `_PASS`) — never production `DB_USER` / `DB_PASS`
- SQL import: streaming gzip with pre-exec validator + `SELECT DATABASE()` session fence before/after each statement
- Forbidden SQL: `USE`, `CREATE/DROP/ALTER DATABASE`, `DELIMITER`, cross-database `` `db`.`table` ``
- Uploads: extract package `uploads.zip` into `{restore_work}/{job_id}/staging_uploads` only
- Post-restore: staging DB postcheck + DRV-style staging report artifact
- Outputs: `staging_restore_manifest.json`, `restore_report.json` under job directory
- Job lifecycle: enforced transitions through `awaiting_owner_approval` — **no production merge**, **no country restore**
- Restore lock: stale lock TTL (6h) + PID liveness; active locks never removed

**Failure policy:**
- Production DB and production uploads are never written (fail-closed SQL validator + staging-only credentials + session checks)
- On any failure after staging wipe/import begins: `staging_dirty=true` on job, rollback anchor preserved if Stage 3 succeeded, exact `stage_failed` recorded, no automatic retry

**NOT in 2B.1:** Country restore, production merge, Admin UI, restore APIs, automatic/scheduled restore, mysqldump routine import.

Phase 2D.1 — Full production merge remaining cutover (ARCHITECTURE APPROVED — PARTIAL)
================================================================================

**Status:** Database cutover (2D.2), uploads cutover (2D.3), **post-validation + manual rollback (2D.4)**, and
**Full Restore end-to-end orchestrator (2E)** are **implemented**. **Country Production Merge remains not implemented.**

**Goal:** Promote a job in `approved_for_merge` to production (`production_merged` →
post-validation → `completed`) using CLI-first orchestration only. Country merge remains
Phase 2D.2 (separate permission, engine, audit scope).

**Selected DB strategy:** Validated staging export → controlled production replace (Strategy D).
Export the already-validated staging database to a merge-ready artifact under the job
directory, then wipe and stream-import into production using the same SQL safety pipeline
as Phase 2B.1 (validator + `SELECT DATABASE()` session fence), with production identity
checks. Does **not** re-import directly from package (staging is the proof).

**Selected uploads strategy:** Staged full-tree directory swap.
Build `uploads_next` from `{restore_work}/{job_id}/staging_uploads/`, pre-snapshot live
`uploads/`, then near-atomic cutover:
  `uploads` → `uploads_pre_merge_{job_id}` ; `uploads_next` → `uploads`
Traversal/symlink/junction protection reuses 2B.1 rules. No partial merge for full disaster.

**Owner Decision — Production Merge Credentials (permanent, 2026-07-13):**
Production Merge must **never** use the normal application MySQL account (`DB_USER` /
`DB_PASS`). A **dedicated** server-only account is mandatory:

  ORANGE_RESTORE_MERGE_DB_USER
  ORANGE_RESTORE_MERGE_DB_PASS

Rules:
- Must differ from `DB_USER` / `DB_PASS` and from `ORANGE_RESTORE_STAGING_DB_USER` / `ORANGE_RESTORE_STAGING_DB_PASS`
- Production database schema only (`DB_NAME` / `config.php`)
- Minimum privileges required for merge (DDL/DML on production schema only — operator grants manually)
- Never reused by the web application or routine backup/export paths
- Documented in `.env.example.php`, this file, and `ORANGE_BACKUP_RECOVERY_RUNBOOK.md`
- **Fail closed:** if either key is missing, empty, or equals the application/staging user or password, merge aborts before any production write

**Owner Decision — Uploads cutover volume safety (permanent, 2026-07-13):**
Before any production uploads cutover, the merge engine **must** verify that live
`uploads/` and prepared `uploads_next/` reside on the **same filesystem / volume** so
directory rename is atomic on the approved path.

- If not on the same volume: **abort merge fail-closed** before any production uploads modification
- **Forbidden fallbacks:** recursive copy, merge, move, copy-then-delete, or any non-atomic alternative
- Rationale: owner approved directory rename as the only production uploads cutover strategy; if atomic rename cannot be guaranteed, merge must not proceed

**Mandatory merge preconditions (summary):**
- Job `status === approved_for_merge`; 2C approval token consumed; approval binding checksums unchanged
- Live package, staging manifest, and rollback anchor checksums match job + approval binding
- Rollback anchor = this job's Stage-3 fresh full disaster backup only (`rollback_anchor_job_only=true`)
- Staging validation gate pass (re-read artifacts + optional live staging sanity)
- Staging DB identity verified; production DB identity verified; names differ
- Dedicated merge credentials present and fenced (see above)
- Global restore lock held; maintenance mode enabled and verified before first production write
- Super Admin + `backup_restore_full` + merge-time password re-auth + exact phrase `RESTORE`

**Merge pipeline (ordered — no stage skipped):**
precheck → lock → maintenance on → maintenance verify → export staging DB → verify export →
pre-merge uploads snapshot → build uploads_next → **same-volume check (uploads vs uploads_next)** →
merge_started → production DB cutover → database_cutover_complete → uploads directory swap →
uploads_cutover_complete → production_merged → post-validation → maintenance off → completed

**Job states (2D.1):** `merge_started`, `database_cutover_complete`, `uploads_cutover_complete`,
`production_merged`, `post_validation_passed`, `failed_merge`, `failed_post_merge`,
`rollback_in_progress`, `rolled_back`, `completed`. No silent retries.

**Rollback:** Only this job's Stage-3 fresh full disaster backup. Pre-merge uploads snapshot for
uploads rollback. No automatic selection of older snapshots.

**NOT in 2D.1 (until cutover implementation phase):** Merge CLI, production DB/uploads cutover,
Admin UI, restore APIs, automatic/scheduled merge, schema changes (unless owner separately approves
`restore_audit_log` table for first mutating phase).
