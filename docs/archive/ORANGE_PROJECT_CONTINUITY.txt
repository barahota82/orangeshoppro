1) AGREED DOMAIN MODEL (conversation) - NOT all implemented in DB yet
----------------------------------------------------------------------

COLORS (target)
- Central color dictionary (canonical colors + translations).
- Product links to colorways (primary/secondary FK to dictionary as previously agreed in chat).
- Customer-facing variant = colorway x size; stock at variant level (aligns with policy file).

SIZES (target)
- No one global flat list for all merchandise types.
- Size FAMILIES (charts): e.g. apparel, shoes EU, bags; each family has SIZE ROWS.
- Product selects ONE size family; variant size_id must belong to that family.
- Advisory size charts (upper / lower / both) are DISPLAY ONLY: programmatic keys (upper|lower|both|none), NOT Arabic strings in code. Arabic is UI copy only.
- Pajama / set: ONE sellable SKU size for the set; guide may show BOTH upper+lower tables; do NOT split into two inventory products for top/bottom (owner rejected split for operational reasons).
- No "two independent sizes on one garment SKU" for your catalog (compound variant excluded).
- Combo/bundle = multiple separate products/SKUs in one offer; not the same as compound variant.

----------------------------------------------------------------------
2) STOCK / ORDERS (agreed policy - see policy file for full text)
----------------------------------------------------------------------
- Stock quantity is per VARIANT (color x size).
- Cart / orders / purchases should reference variant_id.
- Orders: reserve via `orange_order_apply_pending_stock_reservation` (storefront intake in `includes/order_intake_queue.php`, amend in `api/orders/amend-order-items.php`); finalize stock on admin `completed` via `orange_complete_order_fulfillment` (`admin/api/orders/update.php`, `update-status.php`). Line-level partial ship for **sales** is not in admin/schema yet — see **`docs/archive/ORANGE_STOCK_ORDER_POLICY.txt`** §2. Partial **purchase** receipt per line: purchases §6.
- Purchases: increase stock on RECEIPT; partial receipt per line.
- No final deduct without ship; no reserve without availability check.

3) TRANSLATION (implemented pattern in this repo)
----------------------------------------------------------------------
- Shared helper file (single place for translation logic):
  admin/api/lib/translate_names_lib.php
  Uses Google Translate (unofficial client=gtx endpoint) AR->EN, then EN->tl (Filipino) and EN->hi (Hindi).
- Unified HTTP endpoint for name fields:
  admin/api/translate/names.php
  POST JSON: name_ar, name_en (optional) -> returns name_en, name_fil, name_hi.
- Categories also expose admin/api/categories/translate.php (uses same helper pattern).
- Departments + Categories admin UI: Arabic + English fields, "automatic translate" button, debounced auto-translate from Arabic on departments; slug generation from English where applicable.
- DB columns (when migrated): departments/categories support name_fil, name_hi in save/update (code checks column existence).
