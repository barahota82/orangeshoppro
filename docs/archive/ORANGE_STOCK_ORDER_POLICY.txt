Orange - Stock / Orders / Purchases policy (implementation reference)

1) Stock unit = VARIANT (color x size). Each variant has its own qty.
   Cart, orders, purchases must reference variant_id.

2) Orders: RESERVE when the storefront checkout persists the order, then finalize stock on completion/shipment per fulfillment code.
   Partial ship allowed (policy target): deduct per order line when that line ships — verify admin/shipping paths separately if extended.

   Orange implementation — reserve trigger (not TBD):
   - Function: `orange_order_apply_pending_stock_reservation()` in `includes/order_stock.php` (idempotent per `ORDER-{order_number}` in `stock_movements`, `type = 'pending_order'`; decrements `product_variants.stock_quantity` with availability check).
   - Primary call: `orange_storefront_execute_checkout_payload()` in `includes/order_intake_queue.php`, immediately after inserting `orders` + `order_items`, same DB transaction.
   - Customer amend: `api/orders/amend-order-items.php` — `orange_order_release_pending_stock_reservation()` → replace lines → `orange_order_apply_pending_stock_reservation()` again.
   - Completion: `orange_complete_order_fulfillment()` in `includes/order_fulfillment.php` — if a web `pending_order` reserve exists for the order number, stock is not deducted again on complete; movements may be relabeled (`pending_order_fulfilled`). Other order sources handled in the same function.
   - Admin sales orders (today): `admin/api/orders/update.php` and `admin/api/orders/update-status.php` move the whole order to `completed`, which calls `orange_complete_order_fulfillment()`. There are no `order_items` shipped/partial columns — **line-level partial ship for outbound sales** is not implemented in UI/schema yet; **inbound** partial receipt exists for purchases (§4).

3) Cancel / edit after reserve:
   - Cancel before ship: release all reservations.
   - Edit line qty/color/size: validate stock, release old reserve + create new reserve for updated line.

4) Purchases: increase stock on RECEIPT. Partial receipt allowed per purchase line.

5) Safety: no final deduct without ship (or explicit equivalent event). No reserve without availability check.

6) Admin purchases — implementation paths (Orange; stock on receipt per §4)
   - Schema: purchase_items.qty_received (INT, default 0); migration + legacy backfill qty_received = qty in includes/catalog_schema.php.
   - Save invoice without stock bump: admin/api/purchases/create.php and admin/api/purchases/update.php insert lines with qty_received = 0 when column exists; variant stock is not increased until receipt.
   - Receipt: admin/api/purchases/receive.php (mode all or lines); partial line data for UI: admin/api/purchases/lines.php.
   - Edit load + fiscal lock check: admin/api/purchases/get.php; POST update/delete: admin/api/purchases/update.php (reverses stock using qty_received only before replacing lines).
   - UI: admin/pages/purchases.php — استلام كامل / استلام جزئي / تعديل / حذف.

7) كارت الصنف (item_card) — تقرير حركة صنف موحّد (قرار المالك 2026-06-14)
   - الصفحة: admin/pages/item_card.php (تُفتح لكل صنف من شاشة المستودع admin/pages/stock.php «فتح الكارت»، ومُحال إليها من تقارير المخزن).
   - المشكلة المُعالَجة: stock_movements لا يسجّل **الشراء ولا مردود الشراء** (يحدّثان كمية المخزن وطبقات FIFO فقط عبر orange_warehouse_apply_variant_delta). فكان «رصيد أول المدة (تقديري)» القديم خاطئاً والمشتريات غائبة عن الكرت.
   - الحل: الكرت يجمع الحركات من كل المصادر:
       * مشتريات (+): purchase_items + purchases.created_at
       * مردود مشتريات (−): purchase_return_items + purchase_returns.created_at
       * مبيعات (−): stock_movements types delivered_order / pending_order_fulfilled
       * مردود مبيعات (+): stock_movements types order_return / delivered_order_void / order_amend_release
       * تعديل/تسوية (±): stock_movements types manual_adjustment / inventory_count / opening_balance
       * حجز/إفراج وأخرى (±): بقية أنواع stock_movements (لإبقاء الرصيد متّزناً)
   - الرصيد الافتتاحي يُحسب عكسياً: الافتتاحي = الرصيد الفعلي الحالي − صافي كل الحركات (من كل المصادر) التي تاريخها ≥ «من». فيطابق الرصيد الختامي المخزون الفعلي عندما «إلى» = اليوم (أو بلا مدى) — تُعرض مطابقة صريحة.
   - قرار المالك: تُعرض التعديلات/تسويات الجرد كصف مستقل ضمن الكرت حتى يطابق الرصيد الختامي المخزون الفعلي تماماً (وليس الاكتفاء بالشراء/البيع ومردودهما).
   - **مُلغى (قرار المالك 2026-06-15):** صفحة «كارت الصنف» (item_card) **حُذفت** — لا تظهر في المستودع ولا في التقارير. حُذف admin/pages/item_card.php وأُزيل من admin/index.php والتنقّل والصلاحيات والروابط في stock.php وheader.php. نفس نتيجة الكرت متاحة في «تقارير المخزن» (admin/pages/stock_reports.php) تبويب «حركة المخزون» (كشف مُجمّع لكل صنف برصيد أول/جارٍ/ختامي) و«ملخص الحركة».

8) جرد المخزون = تقرير/عَدّ فقط (قرار المالك 2026-06-15)
   - الصفحة admin/pages/inventory_reconciliation.php صارت **تقرير عَدّ فقط**: يُجرى الجرد، يُظهر فرق الكمية وقيمته التقديرية، ثم يُقفل («إقفال التقرير») ليُطبع ويُرفع للإدارة بالتوقيعات.

8b) أرشيف الجرد — إعادة توظيف الشاشة (قرار المالك 2026-06-16)
   - بعد ضبط **تقرير الجرد القابل للطباعة** (تقارير المخزن ← تبويب «الجرد/الأرصدة» مع التوقيعات وأعمدة الكمية الفعلية)، صار العَدّ الرقمي داخل الشاشة القديمة بلا فائدة (لا أثر مخزني/محاسبي). قرار المالك: **تحويل admin/pages/inventory_reconciliation.php إلى «أرشيف الجرد»** (تسمية القائمة في header.php: «أرشيف الجرد»).
   - **الوظيفة:** أرشفة كل عملية جرد تمّت كسجل = (المخزن **أو** عهدة مندوب) + تاريخ الجرد + ملاحظة + **مرفقات** (رفع تقرير الجرد المطبوع الموقّع). **حُذف** إدخال الكميات الفعلية وحساب الفروق من الشاشة (دوال الأسطر/الاعتماد القديمة باقية في includes/inventory_reconciliation.php للتوافق لكنها غير مستعملة من الشاشة).
   - **الأنواع المسموحة للمرفقات:** PDF + صور (عدا SVG) + Excel (xlsx/xls) + Word (docx/doc)؛ **عدة مرفقات** لكل سجل (حتى 20، حتى 25MB لكل ملف). xlsx/docx حاويات zip — يُسمح بها بالامتداد عند اكتشاف finfo نوعاً عاماً (zip/octet-stream).
   - **التخزين:** ملفات تحت project_root/uploads/stocktake/{id}/ (غير عام — التنزيل عبر سكربت يتحقق من الجلسة) وقائمة JSON في العمود inventory_reconciliation.attachments_json (نمط مرفقات المورد). أُضيف العمودان attachments_json TEXT وdelivery_agent_id (اختياري) عبر ensure-schema في includes/acc10_schema.php. عند اختيار مندوب يُسند warehouse_id للمستودع الافتراضي للدولة (قيد NOT NULL) ويُخزَّن delivery_agent_id.
   - **المنطق:** دوال orange_inventory_reconciliation_archive_{save,list,get,delete,nav,search} في includes/inventory_reconciliation.php + مكتبة المرفقات includes/stocktake_archive.php (تخزين/تحقق/ترميز آمن بنمط supplier_attachments). **API:** admin/api/inventory-reconciliation/{archive-save,archive-delete,attachment-upload,attachment-download,attachment-delete,archive-nav,archive-search}.php. (نقاط save/get/approve القديمة باقية بلا استعمال من الشاشة.)
   - **تخطيط الكارت العلوي + تنقّل/بحث بنمط سند القيد (قرار المالك 2026-06-17):** حُذفت الفقرة التعريفية الزرقاء أعلى الشاشة. الكارت العلوي = سطر أول (ترتيب | المخزن/المندوب | تاريخ الجرد | عدد المرفقات | زر «إدارة المرفقات» | مجموعة تنقّل) ثم سطر «ملاحظات» بعرض كامل ثم شريط سفلي بأزرار «جديد | حذف | حفظ». **مجموعة التنقّل** بنمط journal_voucher_screen: أزرار «<< أول / < سابق / > تالي / >> آخر» (تنقّل خلفي فعلي عبر كل السجلات بترتيب id عبر archive-nav.php) + زر «بحث» يفتح **نافذة بحث منبثقة** (فلاتر: تاريخ من/إلى + المخزن/المندوب + ملاحظة تحتوي نصاً؛ جدول نتائج يُفتح السجل بالنقر) عبر archive-search.php. **أُزيل** كارت «استرجاع الأرشيف» السفلي القديم (استُبدل بنافذة البحث؛ archive-list.php باقٍ بلا استعمال من الشاشة).
   - **إضافة المرفقات قبل الحفظ + إلزامية المرفق + طباعة (قرار المالك 2026-06-17):** غُيّر أسلوب «احفظ أولاً ثم أرفق» إلى **تخزين مؤقت حقيقي**: للسجل الجديد تُرفع المرفقات إلى مجلد مؤقت `uploads/stocktake/_drafts/{token}/` (token عشوائي 32hex يُولَّد لكل تحميل صفحة) ولا يُنشأ صف في القاعدة، ثم عند «حفظ» تُنقَل الملفات إلى `uploads/stocktake/{id}/` وتُسجَّل في attachments_json. **الحفظ مشروط** بـ: اختيار مخزن/مندوب + تاريخ + **مرفق واحد على الأقل** (تحقق في الواجهة وفي archive-save.php؛ للتعديل يلزم بقاء مرفق واحد). دوال جديدة في includes/stocktake_archive.php: is_valid_draft_token / ensure_..._draft_dir / finalize_draft / cleanup_draft / cleanup_old_drafts (تنظيف المسودات المهجورة > يوم). نقاط attachment-{upload,delete,download}.php دعمت فرع المسودة (id<=0 + token + path، مع تحقق المسار داخل مجلد المسودة). زر **«طباعة»** في شريط أزرار الكارت يفتح **صفحة مستند** (رقم المستند + المخزن/المندوب + التاريخ + الملاحظة + خانات توقيع) وبها زران **«طباعة»** و**«إغلاق»** بدل الطباعة التلقائية المباشرة، لتوحيد السلوك مع المورد. **عمود المرفقات** في جدول السجلات أصبح زر «عرض (N)» يفتح السجل ونافذة المرفقات تلقائياً (param att=1). **رقم المستند** = حقل sort_order يُقترَح تلقائياً = MAX+1 مع منع ظهور/حفظ القيمة 0 (الحد الأدنى 1). طباعة المرفقات نفسها: PDF/صور inline في المتصفح، Office تُنزَّل ثم تُطبع (مطابق لمرفقات المورد).
   - **تحسين قابلية العرض (قرار المالك 2026-06-17):** توسيع نافذة «إدارة المرفقات» في **المورد** و**أرشيف الجرد** لتفادي تراكب النص، مع إعادة ترتيب شريط الرفع داخل المودال إلى صفين واضحين (ملف ثم وصف + زر الرفع) حتى لا تتداخل الكلمات، وتوسيع عرض حقل «تاريخ الجرد» في صف «سجل جرد جديد».
   - **تعديل التسمية (قرار المالك 2026-06-18):** في **شاشة الصلاحيات** و**فهرس المخازن والمشتريات** يعتمد الاسم **«أرشيف الجرد»** بدل «تسوية المخزون / الجرد».
   - **التطبيق الفعلي للفروق على المخزون والمحاسبة يبقى عبر «قيد تسوية مخزون» (SAJ)** — البندان 9 و11.

9) سند تعديل الرصيد (Stock Adjustment Voucher) — السند التنفيذي للتعديل (قرار المالك 2026-06-15)
   - الصفحة admin/pages/stock_adjustment_voucher.php + API admin/api/stock-adjustment/{save,get,approve}.php + المنطق includes/stock_adjustment_voucher.php (جداول stock_adjustment_voucher + stock_adjustment_voucher_line عبر ensure-schema بنمط catalog_schema).
   - يُحرَّر **بعد قرار الإدارة** الناتج عن تقرير الجرد. متعدد الأسطر؛ لكل سطر صنف (variant) + خانة **إضافة (+)** وخانة **خصم (−)** → الفرق. قيمة الفرق = الكمية × تكلفة الصنف (FIFO الحالية/الاحتياطي).
   - **المعالجة المحاسبية لكل سطر** (قرار المالك): يُختار حساب ورقة-ترحيل من شجرة الحسابات — إمّا **أرباح/خسائر** أو **ذمة موظف** (أي حساب leaf، يُحمَّل عليه المبلغ). المخزن = المستودع الافتراضي لدولة الأدمن.
   - عند الاعتماد (approve): يُطبَّق الفرق على المخزون + طبقات FIFO (زيادة→طبقة adjust بتكلفة الطبقات الحالية، نقص→استهلاك FIFO) + يُرحَّل قيد GL لكل سطر: زيادة ⇒ مدين المخزون / دائن حساب المعالجة؛ نقص ⇒ دائن المخزون / مدين حساب المعالجة (خسارة أو ذمة موظف). يدعم طابور الترحيل المعلّق إن كان مفعّلاً.
   - حركة المخزون تُسجَّل type=manual_adjustment مرجع STK-ADJ-{id} فتظهر في تقارير المخزن.

10) شاشتا المخزون بنمط سند القيد (للكميات) (قرار المالك 2026-06-15)
   - القرار يُلغي التعليمة السابقة «لا تلمس أرصدة أول المدة»: صارت **أرصدة أول المدة المخزنية سنداً كاملاً** (رقم سند + حفظ مسودة/اعتماد/تنقّل بين السندات/بحث/طباعة بعد الحفظ) بنمط سند القيد لكن للكميات.
   - **أرصدة أول المدة (كميات فقط، بلا GL):** المنطق includes/opening_stock_voucher.php (جداول opening_stock_voucher + opening_stock_voucher_line عبر ensure-schema بنمط catalog_schema مع orange_schema_invalidate_table_exists بعد كل CREATE) + API admin/api/opening-stock-voucher/manage.php (actions: get/save/delete/approve/variant_info) + الصفحة admin/pages/opening_stock_balances.php. **سند واحد لكل دولة** (مثل رصيد أول المدة المالي — orange_opening_stock_voucher_get_singleton؛ لا تنقّل ولا بحث ولا «سند جديد»). الواجهة بنمط jv-voucher-print-sheet الظاهر (ترويسة طباعة + إطار السند). عند الاعتماد: لكل سطر تُضبَط كمية المتغيّر في المستودع الافتراضي للدولة كرصيد افتتاحي (orange_warehouse_set_variant_quantity + حركة opening_balance، مرجع OPEN-STK-{id}) بلا تكلفة ولا قيد. يُمنع الاعتماد إذا كان الإقفال (orange_opening_stock_is_locked) مفعّلاً؛ مفتاح «مقفول» باقٍ في الشاشة. الجانب المالي يبقى في «أرصدة أول المدة المالية» المنفصلة.
   - **سند تعديل الرصيد:** أُعيد تصميم واجهته بنمط سند القيد الظاهر (jv-voucher-print-sheet + ترويسة طباعة + jv-voucher-header-line + admin-doc-lines-table) مع تنقّل/بحث؛ منطق الحفظ/الاعتماد/التكلفة/قيد GL كما هو (البند 9). اختيار الصنف وحساب المعالجة بنقرتين (نافذة بحث). أُضيفت دوال nav/search/next_no إلى includes/stock_adjustment_voucher.php وactions مقابلة في admin/api/stock-adjustment/get.php.
   - **منتقي مشترك:** admin/partials/product_pick_modal.php (window.OrangeProductPicker.open) — نافذة بحث منتجات (variants_search) بنقرتين على خانة الكود، تستعملها الشاشتان؛ إثراء الكود/الرصيد/التكلفة عبر variant_info الخاص بكل شاشة. تواريخ الشاشتين يوم/شهر/سنة (orange-inp-dmy) وبلا حدود أسطر. صلاحيات API: opening-stock-voucher ← صفحة opening_stock_balances في includes/admin_permissions.php.

11) سند تعديل الرصيد → مستند محاسبي يشغّله المحاسب (قرار المالك 2026-06-15)
   - **نُقلت الشاشة** من «المخازن والمشتريات → المخزون» إلى «الحسابات والتقارير → السندات والذمم» (بجانب «سند قيد») في includes/admin_nav_tree.php، ومجموعة الصلاحية تغيّرت stock_adjustment_voucher: warehouse ⇐ accounting في includes/admin_permissions.php. السبب: التوجيه المحاسبي (ذمة موظف مقابل أرباح/خسائر) قرار محاسبي يخص المحاسب، وفصل من يَعُدّ (أمين المخزن في تقرير الجرد) عمن يُوجّه ويعتمد (المحاسب) ضبط داخلي. «أرصدة أول المدة المخزنية» تبقى في المخازن (بلا أثر محاسبي). تقرير الجرد (inventory_reconciliation) يبقى في المخازن لأمين المخزن.
   - **تنفيذ (2026-06-15) — المعالجة على مستوى السند بشبكة مدين/دائن مرنة (يُلغي «حساب لكل سطر» في البند 9):**
     * **شبكة كميات بلا حساب معالجة:** أزيل عمود «حساب المعالجة» من أسطر الكميات (الكود/الاسم/اللون-المقاس/الرصيد/إضافة/خصم/التكلفة/قيمة الفرق فقط). أُسقط treatment_account_id من المنطق (العمود يبقى NULL للتوافق مع سندات قديمة).
     * **كارت سفلي «المعالجة المحاسبية (قيد التسوية)»:** شبكة مرنة (حساب ورقة-ترحيل + مدين + دائن + بيان، سطر واحد أو أكثر) بنمط سند القيد. يعرض «حركة المخزون التلقائية» (مدين عند الزيادة/دائن عند النقص بقيمة FIFO) و«صافي المعالجة المطلوب» ومؤشّر اتزان حيّ + زر «موازنة تلقائية». حساب المخزون **يُضاف تلقائياً** عند الاعتماد ولا يُختار في الشبكة.
     * **القيد عند الاعتماد:** سطر(أسطر) المخزون التلقائية (Dr إجمالي الزيادات / Cr إجمالي النواقص بقيمة طبقات FIFO) + أسطر المعالجة المُدخَلة، مع تحقّق أن صافي (دائن−مدين) للمعالجة = صافي قيمة المخزون، وتحقّق اتزان نهائي (مدين=دائن) قبل الترحيل.
     * **نوع يومية مستقل «قيد تسوية مخزون» (SAJ):** أُضيف إلى orange_journal_types_canonical_rows + خريطتا entry_type=stock_adjustment ↔ SAJ في includes/journal_types.php. يُرحَّل القيد بـ entry_type=stock_adjustment (بدل general/JE) في مساري orange_voucher_post والطابور المعلّق — فيُصفّى/يُعدّ/يُراجَع/يُقفل منفصلاً في اليومية. المرجع STK-ADJ-{id} باقٍ.
     * **المخطط:** جدول stock_adjustment_voucher_gl (voucher_id, line_no, account_id, debit, credit, memo؛ CASCADE) عبر ensure-schema بنمط catalog_schema. الملفات: includes/stock_adjustment_voucher.php (normalize_gl_lines/get_gl_lines + save/get/approve)، admin/api/stock-adjustment/save.php (تمرير gl_lines)، admin/pages/stock_adjustment_voucher.php (الكارت السفلي + JS).
     * **ملاحظة تشغيلية:** مبالغ المعالجة يحفظها المحاسب؛ قيمة المخزون تُحسب بـ FIFO عند الاعتماد — إن اختلفت عن التقدير وقت المسودة (خاصة نقص يستهلك طبقات بتكلفة أقدم) يُرفض الاعتماد برسالة تبيّن الصافي المطلوب، فيعدّل المحاسب ويعيد.

   - **تعطيل (إخفاء من المتجر):** المسار **الاعتيادي** — `admin/api/products/toggle.php` → `products.is_active = 0` (الواجهة تستعمله من `admin/pages/products.php`). **لا** يُغيّر `delete.php` حالة `is_active` تلقائياً عند الرفض.
   - **يُمنع الحذف النهائي** إن وُجد أيّ من: `order_items` · `purchase_items` · `purchase_return_items` · `sales_return_items` · `stock_movements` (product_id أو variant_id) · `warehouse_variant_stock` بكمية ≠ 0 · `inventory_cost_layers` · `inventory_cost_consumptions` · `inventory_reconciliation_line` · `stock_adjustment_voucher_line` · أعمدة هدايا الطلب `orders.cart_gift_variant_id` / `cart_bogo_gift_variant_id` لمتغيّرات هذا المنتج · أي قاعدة عروض سلة/كومبو/BOGO/هدية ما زالت تشير للمنتج داخل أعمدة المنتج أو JSON.
   - **عند المنع:** `admin/api/products/delete.php` يُرجِع **422** برسالة واضحة: عطّل المنتج (`is_active = 0`) بدلاً من الحذف — **دون** تعديل `is_active`.
   - **ممنوع:** `DELETE FROM stock_movements` ضمن مسار حذف المنتج — السجل التاريخي للمخزون يبقى.
   - **إن سُمح الحذف:** يُزال catalog-only فقط: `offers` · `product_channels` · `product_images` · `product_attribute_values` · `product_colorway_images` · `product_colorways` · `warehouse_variant_stock` (صفوف المتغيّرات) · `product_variants` · `products` — **لا** طلبات/مشتريات/مردودات/FIFO/GL.
   - **تنفيذ:** `includes/product_delete_policy.php` (فحص) + `admin/api/products/delete.php`.

17) إكمال الطلب المزدوج المتزامن — ISSUE-05 (قرار مالك — مؤكَّد، مؤجَّل — 2026-07-01)
   - **المشكلة (مؤكَّدة):** طلبَا «تم التسليم» (`completed`) متزامنان على نفس `orders.id` يمكن أن يمرّا كلاهما حارس `orange_order_stock_fulfillment_already_done()` (قراءات بلا قفل) فيُنفَّذ `orange_complete_order_fulfillment()` مرتين — خصم مخزون مزدوج (`delivered_order`) و/أو استهلاك FIFO مزدوج؛ أشدّه على الطلبات **بلا** حجز `pending_order` (مسار يدوي/أدمن).
   - **المسارات المتأثرة:** `admin/api/orders/update-status.php` · `admin/api/orders/update.php` · `admin/api/orders/bulk-update-status.php` → `orange_complete_order_fulfillment()` في `includes/order_fulfillment.php`.
   - **الإصلاح الم minimal المقترَح (FOR UPDATE على صف الطلب فقط):** **مرفوض كـ patch معزول** — يُ serializes إكمالاً مزدوجاً لكنه يعكس ترتيب القفل الحالي لمسارات **تعديل/إلغاء** الحجز: amend/cancel تُقفل `warehouse_variant_stock` (وتحرّر الحجز) **قبل** `UPDATE orders`، بينما الإكمال سيقفل `orders` **قبل** مخزون/FIFO — خطر **deadlock (1213)** عند تداخل amend/cancel مع complete على نفس الطلب (مثلاً `approved` + تعديل عميل + تسليم أدمن).
   - **قرار معماري:** الإصلاح **الآمن** يتطلّب **توحيد ترتيب القفل** عبر مسارات الإكمال + التعديل + الإلغاء (ويفضّل ترتيباً ثابتاً على `orders.id` في التحديث الجماعي) — **لا** `SELECT … FOR UPDATE` على `orders` في نقاط الإكمال وحدها دون ذلك.
   - **الحالة:** **مؤجَّل** حتى جلسة «lock-order harmonization» مخطَّطة؛ **لا تنفيذ** ISSUE-05 في الريبو قبلها.
